# genpass — вопросы и ответы для собеседования
## Java Developer (Junior → Middle)

Подготовка по реальному пет-проекту: **genpass** — state-less офлайн-генератор паролей /
passphrase / PIN (Java 21, Maven, встроенный JDK HttpServer, ванильный JS-UI, Docker
multi-arch amd64/arm64/armv7 для деплоя на Synology NAS).

Метки сложности: ●○○ — Junior, ●●○ — уверенный Junior/Middle, ●●● — Middle+ (каверзные).

## 0. Питч проекта за 60 секунд

> «Это офлайн-генератор паролей: веб-приложение на Java 21 без единого стороннего
> фреймворка в рантайме. Ядро генерации — чистый JDK: `SecureRandom`, гарантия, что в

> и хардненинг-итерацию.»

## 1. Архитектура и дизайн

**Вопрос 1. Расскажи про архитектуру проекта. ●○○**
Два слоя с односторонней зависимостью:
- `org.example.genpass.core` — ядро генерации: `CryptoRandom`, `CharGroups`, records-опции
  (`PasswordOptions`, `PassphraseOptions`, `PinOptions`), генераторы (`PasswordGenerator`,
  `PassphraseGenerator`, `PinGenerator`), `Wordlist`, `StrengthEstimator`.
- `org.example.genpass.web` — HTTP: `WebServer`, `ApiHandlers`, `StaticHandler`,
  `SecurityHeaders`, `HealthCheck`.

Ключевое правило: зависимости направлены только внутрь — `web → core`, а ядро не знает
про HTTP и Jackson (проверяется поиском импортов). Благодаря этому ядро тестируется
чистыми unit-тестами без поднятия сервера, а веб-слой — тонкий: разобрал JSON →
вызвал ядро → сериализовал ответ.

**Вопрос 2. Почему не Spring Boot? ●●○**
Spring отсутствовал в зависимостях и избыточен: приложение state-less, один процесс,
три POST-эндпоинта и статика. Встроенный `jdk.httpserver` даёт ноль новых зависимостей
(меньше CVE-поверхность и размер образа), многопоточность — через `ExecutorService`.
Это осознанный трейд-офф: больше ручного кода (роутинг, ошибки), но для LAN-инструмента
это приемлемо и проще аудировать. На собеседовании важно показать, что выбор — решение,
а не незнание Spring.

**Вопрос 3. Зачем DTO-records, а не мапы? ●○○**
Типобезопасность и самодокументируемость: `record PasswordRequest(int length, boolean
lowercase, ...)` задаёт контракт API. Неизвестное поле в JSON → 400 автоматически
(Jackson по умолчанию `FAIL_ON_UNKNOWN_PROPERTIES`), опечатка в ключе не пройдёт молча,
как с `Map<String, Object>`.

**Вопрос 4. Почему validation в конструкторах records, а не в сервисах? ●○○**
Инварианты объекта должны держаться самим объектом: `PasswordOptions` с длиной 3
просто не может существовать — компактный конструктор бросит `IllegalArgumentException`
(границы 4–128, хотя бы один набор). Тогда ни генератору, ни оценщику энтропии не нужно
повторять проверки, и «битый» объект не просочится вглубь. Валидируем на границе системы.

## 2. Java Core

**Вопрос 5. Что такое record? Чем отличается от класса? ●○○**
Короткая неизменяемая модель данных: автоматически получает конструктор со всеми полями,
`equals`/`hashCode`/`toString` и аксессоры. В проекте — опции генерации и DTO.
Ключевое: поля `final`, класс финальный — неизменяемость «из коробки», что важно для
объектов-конфигураций. Если нужна валидация — компактный конструктор (без списка
параметров, с ними — тело).

**Вопрос 6. Почему почти все классы final, а конструкторы приватные? ●○○**
`final`-класс запрещает наследование — для утилитных классов (например, `CharGroups`,
`StrengthEstimator`) наследование бессмысленно и опасно. Приватный конструктор +
`static`-методы — паттерн «утилита» (как `Collections`). Неизменяемость упрощает
рассуждения о потокобезопасности: объект без состояния или с `final`-полями безопасно
шарить между потоками.

**Вопрос 7. Зачем `List.copyOf` в `Wordlist`? ●○○**
Возвращает неизменяемую копию: после загрузки словарь не может быть изменён извне
(защитное копирование). Словарь грузится один раз и шарится между всеми запросами —
неизменяемость делает это безопасным без синхронизации на чтении.

**Вопрос 8. Где в проекте switch-expression? ●○○**
`StaticHandler.resourceFor()`: маппинг пути на ресурс через `switch`-expression
(`case "/" -> "/web/index.html"; ...`). Без `break`, без проваливаний, выражение —
компактнее и безопаснее старого `switch`-statement.

**Вопрос 9. try-with-resources: где используется и почему это важно? ●○○**
Везде, где открываются ресурсы: чтение словаря (`BufferedReader` из `InputStream`),
тело ответа (`OutputStream`), чтение файла в `StaticHandler`. Гарантирует `close()`
даже при исключении. Ручной `close()` в `finally` остался только у `HttpExchange` —
это не `AutoCloseable`-паттерн сервера, там свой жизненный цикл.

## 3. Многопоточность

**Вопрос 10. Как устроен пул потоков и graceful shutdown? ●●○**
`WebServer` создаёт `HttpServer` с `ExecutorService.newFixedThreadPool(4)` — JDK-сервер
сам не плодит поток на запрос, а берёт из пула (ограничение ресурсов). Остановка:
shutdown-hook в `App.main` вызывает `server.stop(1)` (до 1 секунды на завершение
in-flight запросов) и `executor.shutdown()` — потокобезопасная остановка без
«висящих» запросов.

**Вопрос 11. Почему shared `SecureRandom` безопасен, а shared `Random` — нет? ●○○**
`SecureRandom` потокобезопасен (внутренняя синхронизация), `java.util.Random` тоже
атомарен на seed, но дело не в этом: `Random` — не криптостойкий (линейный конгруэнтный,
предсказуем по нескольким значениям). В проекте единый `CryptoRandom.INSTANCE` —
«один экземпляр SecureRandom на JVM» (требование спеки проекта).

**Вопрос 12. Как устроен ленивый синглтон `Wordlist.getDefault()`? ●●○**
Double-checked locking: `volatile`-поле + `synchronized`-блок с повторной проверкой —
дорогая загрузка (чтение 1296 строк из jar) выполняется один раз, параллельные потоки
не блокируются на чтении после инициализации. `volatile` гарантирует видимость
полностью сконструированного объекта.

**Вопрос 13. Утечки: на что обращать внимание с HttpServer? ●●○**
Каждый `HttpExchange` обязан быть закрыт (`exchange.close()` в `finally`) — иначе
утечка дескрипторов и «висящие» соединения. Это классическая болевая точка ручного
HTTP-слоя, и в проекте закрытие вынесено в `finally` во всех хендлерах.

**Вопрос 14. Почему пул из 4 потоков, а не «по потоку на запрос»? ●●○**
«Поток на запрос» не масштабируется: при 100 параллельных запросах — 100 потоков и
переключение контекста. Фиксированный пул ограничивает потребление и даёт
предсказуемость; для генератора (задача на микросекунды, без I/O-блокировок) 4 потока
с запасом. Для CPU-bound задач оптимален пул ~= числу ядер (можно было взять
`availableProcessors()`).

## 4. Безопасность и криптография

**Вопрос 15. Почему `SecureRandom.nextInt(bound)`, а не `random.nextInt() % bound`? ●●○**
`% bound` даёт **modulo bias**: при `bound`, не делящем 2³¹, младшие значения
встречаются чаще (например, `% 10` на 2³¹ значениях: остатки 0–7 встречаются чаще,
чем 8–9). Для генератора паролей это измеримое смещение в распределении — атакующий
получает преимущество. `nextInt(bound)` внутри JDK делает rejection sampling —
равномерно.

**Вопрос 16. Что такое энтропия пароля и как она считается? ●●○**
Энтропия = `log2(размер пространства)`. Для случайного пароля: `длина × log2(размер
алфавита)`. Примеры из проекта: 8 строчных букв = `8 × log2(26)` ≈ 37.6 бит;
passphrase из 5 слов словаря в 1296 слов = `5 × log2(1296)` ≈ 51.7 бит — длинная
фраза из словаря сильнее короткого «сложного» пароля. Словесные метки: <40 слабый,
40–59 средний, 60–79 сильный, ≥80 очень сильный. Плюс справочное время перебора при
10¹⁰ попыток/сек: `2^биты / 10^10` секунд.

**Вопрос 17. Зачем в оценке энтропии учитывать `excludeAmbiguous`? ●●○**
Флаг исключает символы `I l 1 O 0` — они неоднозначны при вводе. Но исключение
**уменьшает алфавит**: полный пул из 4 наборов — 89 символов, после исключения — 84
(из lower уходит `l`, из upper — `I`,`O`, из digits — `1`,`0`; `|` в спецнаборе проекта
нет, поэтому фильтр для него — no-op). Если оценку не корректировать, она будет
завышенной — «честность оценки» была отдельным требованием.

**Вопрос 18. Почему passphrase с цифрой добавляет ровно ~3.32 бита? ●●○**
`log2(10) ≈ 3.3219` — цифра добавляет один символ из десяти возможных. В проекте
осознанно упростили: цифра добавляется в **конец** одного случайного слова, а не в
произвольную позицию — реализация проще, а оценка остаётся консервативной (не
завышенной: позиция цифры не увеличивает пространство, но и не уменьшает).

**Вопрос 19. Что дают HTTP-заголовки безопасности? ●●○**
- `Cache-Control: no-store` — пароль не должен осесть в кэше браузера/прокси
  (на статике — `no-cache`: переvalidate, но кэшировать можно).
- CSP `default-src 'none'; script-src 'self'; ...` — даже при XSS браузер не выполнит
  инлайн-скрипт или внешний ресурс; поэтому в UI **запрещены инлайн-скрипты** — JS
  только в отдельном `app.js`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (не светим URL с
  паролями в реферрере), `X-Frame-Options: DENY` (защита от clickjacking).

**Вопрос 20. Почему slf4j-nop — это «фича безопасности»? ●●●**
В pom подключён `slf4j-nop` — реализация, которая ничего не пишет. Для приложения,
генерирующего секреты, это гарантия: даже если какая-то библиотека начнёт логировать,
вывод будет пустым. Плюс код сам не логирует результаты: в stdout — только строка
старта. Логирование пароля — это утечка секрета в систему, из которой его потом
невозможно «удалить».

**Вопрос 21. Что значит state-less и зачем это? ●○○**
Приложение не хранит состояние: нет БД, файлов, сессий. Каждый запрос независим.
Следствия: контейнер можно перезапускать/масштабировать без потерь; нечего красть
из «хранилища паролей» — их там нет; поверхностная площадь атаки минимальна.

## 5. HTTP, JSON, веб-слой

**Вопрос 22. Какие эндпоинты и какие статусы? ●○○**
`GET /api/health` (healthcheck), `POST /api/password|passphrase|pin`, статика `/`,
`/app.js`, `/style.css`. Ошибки: 400 — невалидные параметры/JSON, 404 — неизвестный
путь, 405 + заголовок `Allow` — неверный метод, 413 — тело больше 64 КБ.

**Вопрос 23. Почему 405 требует заголовка Allow? ●○**
`Allow` сообщает клиенту, какие методы разрешены на ресурсе (`Allow: POST`) — это
часть HTTP-контракта, клиент может сразу повторить правильным методом.

**Вопрос 24. Как ограничили размер тела и зачем? ●●○**
Чтение тела в буфер с проверкой лимита 64 КБ по ходу чтения → 413. Без лимита
злоумышленник может исчерпать память JVM одним запросом (DoS). Проверка до парсинга
JSON — важно: парсить гигантское тело нельзя.

**Вопрос 25. Зачем path-guard'ы, если контексты уже зарегистрированы? ●●●**
`HttpServer` матчит контекст по **префиксу**: `/api/password` поймает и
`/api/password/x`. Поэтому в хендлере сверяется точный путь, и «хвост» получает 404.
Второй нюанс — порядок проверок: сначала путь, потом метод, иначе `GET /api/password/x`
вернул бы 405 вместо 404 (это был реальный баг, пойманный тестами).

**Вопрос 26. Строгая коэрсия JSON: что это и зачем? ●●○**
Jackson по умолчанию «добрый»: `{"length": "20"}` сконвертирует строку в число,
`{"length": 4.9}` — **молча усечёт** до 4. Для API, генерирующего секреты, это
неприемлемо: отключены `ACCEPT_FLOAT_AS_INT` и `ALLOW_COERCION_OF_SCALARS` → оба
запроса получают 400. Тип контракта должен соблюдаться строго.

**Вопрос 27. Как устроена статика без фреймворков? ●○**
`StaticHandler` отдаёт ровно три файла из classpath (`/web/index.html` и т.д.) с
правильным `Content-Type` и `charset=UTF-8`; любой другой путь — 404. Никакого
листинга каталогов (в classpath его и не может быть «случайно»). HEAD поддерживается
(ответ без тела) — часть HTTP-контракта.

**Вопрос 28. Почему JSON в UTF-8 и с charset в Content-Type? ●○**
JSON по спецификации — UTF-8, но явный `charset=UTF-8` убирает неоднозначность для
клиентов; спецсимволы паролей (`!@#$%^&*()`) и русские метки («средний») должны
корректно экранироваться/декодироваться.

**Вопрос 29. Как работает UI и почему он «офлайн»? ●○○**
Ванильные HTML/CSS/JS, три вкладки-режима, fetch на свой же origin с
`cache: 'no-store'`. Копирование: `navigator.clipboard` (требует secure context —
HTTPS) с fallback на `document.execCommand('copy')` для HTTP в LAN. Никаких CDN,
шрифтов, телеметрии — всё внутри jar. CSP это ещё и подкрепляет: `connect-src 'self'`.

## 6. Тестирование

**Вопрос 30. Какие виды тестов и почему такая связка? ●○○**
Unit (TestNG, 42 теста) — ядро: границы валидации, принадлежность алфавиту, гарантия
покрытия наборов, статистика, энтропия. Интеграционные (rest-assured, 17 тестов) —
веб: старт реального сервера на свободном порту (`ServerSocket(0)`), статусы,
заголовки, схема ответов. TestNG выбран, потому что был в зависимостях шаблона —
но это полноценный фреймворк с suite-файлами (`testNG.xml`), аннотациями
`@BeforeSuite`/`@AfterSuite`.

**Вопрос 31. Как тестировать случайность? ●●●**
Никак «в лоб»: нельзя засидить `SecureRandom` (это сломало бы смысл теста и требует
API для инъекции). Вместо этого — статистика: 100 000 генераций, подсчёт частот,
проверка, что каждая частота в допуске ±20% от равномерной. При 100k испытаний и 26
символах отклонение на 20% — это ~12 сигм: ложное срабатывание практически невозможно,
а реальное смещение генератора тест поймает. Плюс «гарантия покрытия» проверяется
детерминированно: 1000 генераций длины 4 со всеми 4 наборами — в каждой должен быть
символ каждого набора (это инвариант алгоритма, не статистика).

**Вопрос 32. Почему в статистическом тесте длина 4, а не 1? ●●○**
Спека запрещает пароли короче 4 (`PasswordOptions` бросит исключение), поэтому
измерить «символ длины 1» нельзя. Решение: генерировать длину 4 и считать
распределение **первого символа** — распределение то же самое (равномерный выбор),
а валидация не нарушена. Хороший пример, как тест подстраивается под контракт.

**Вопрос 33. Как тестируется энтропия? ●○**
Точечными значениями с допуском: `entropyBits(8 строчных) == 37.60 ± 0.01`.
Интересный кейс: в спеке было «5 слов из 1296 ≈ 51.65 бит», но `5 × log2(1296) =
51.699` — спека была математически неверна, тест писался по правильному значению,
а спека поправлена (это пример, как тесты вскрывают ошибки документации).

**Вопрос 34. Какие негативные сценарии покрыты? ●○**
400: длина 3, 129, 100 слов, все наборы выключены, битый JSON, неизвестное поле,
строка/дробь в числе; 404: неизвестный путь и «хвост» известного; 405 с Allow;
413: тело 70 КБ; 404 API несёт `no-store`.

**Вопрос 35. Что проверяют интеграционные тесты, кроме статусов? ●●○**
Схему ответа (`result`, `entropyBits`, `strength`, `crackTime`), семантику опций
(ровно одна цифра в passphrase, ни одного ведущего нуля в PIN), заголовки
безопасности на ответах. Например, тест парсит passphrase, считает слова и проверяет
капитализацию — это проверка поведения, а не «что сервер ответил 200».

## 7. Реальные баги и уроки (кейсы для рассказа)

**Кейс 1. «Сервер молча рвёт соединение» (NoHttpResponse). ●●●**
Симптом: статика не отвечает — curl получает `000`, rest-assured — `NoHttpResponse`,
при этом API работает. Диагностика: curl-смоук показал, что 404 работают, а 200 с телом
— нет; оказалось, `CONTENT_TYPES` был замаплен по имени файла (`"index.html"`), а
искался ресурс по пути (`"/web/index.html"`) → `Content-Type: null` → NPE в
`Headers.set` → `HttpServer` закрыл соединение без ответа. Урок: (1) не глотать
исключения молча в хендлерах — NPE «съедался» пустым `catch`; (2) смоук реальными
запросами ловит то, что тесты-статусы могут пропустить; (3) мапы должны быть
консистентны по ключам.

**Кейс 2. «Все вкладки видны одновременно». ●●○**
Пользователь сообщил: видны все три формы. Причина — CSS: авторское правило
`.panel { display: flex }` перекрывает браузерное `[hidden] { display: none }`
(авторские стили сильнее UA-стилей). Фикс — `[hidden] { display: none !important; }`.
Урок: атрибут `hidden` «ломается» любым явным `display`; и мой первый браузерный
смоук проверял генерацию, но не видимость — после фикса добавил проверку computed
styles (регрессия).

**Кейс 3. rest-assured: Float вместо Double. ●●○**
Тест `entropyBits` > 0 падал на валидном ответе: rest-assured парсит десятичные JSON
как `Float`, а матчер `greaterThan(0d)` типизирован под `Double`. Решение —
`JsonConfig.numberReturnType(DOUBLE)`. Урок: знать, как твой HTTP-клиент парсит числа,
и типизировать матчеры под это.

**Кейс 4. Порядок проверок: 405 вместо 404. ●○○**
`GET /api/password/x` возвращал 405, потому что метод проверялся до пути. Правильно:
сначала «это вообще наш путь?» → 404, потом метод → 405. Тест зафиксировал.

**Кейс 5. Спека против математики. ●○○**
`51.65` в спеке vs `51.70` по формуле. Тест писали по формуле; спека поправлена с
комментарием. Урок: тесты — источник правды о поведении, документация должна
следовать за ними.

**Кейс 6. Docker: Java 17-образ не запустит jar 21-го класса. ●●○**
Проект переведён на Java 21, а Dockerfile из плана был на temurin-17 — рантайм упал
бы с `UnsupportedClassVersionError`. Плюс для armv7 `openjdk-21` нет в Debian 12 —
проверено по индексу пакетов и выбран Debian 13. Урок: версии компилятора и рантайма
в Docker — часть контракта; проверять пакеты по первоисточнику, а не по догадкам.

## 8. Docker и деплой

**Вопрос 36. Что даёт multi-stage Dockerfile? ●○○**
Два этапа: `build` (maven-образ, компиляция + тесты) и `runtime` (только JRE + jar).
В рантайм-образ не попадают Maven, исходники и кэш зависимостей — меньше размер и
поверхность атаки. Плюс тесты выполняются на этапе сборки: в образ попадает только
проверенный артефакт.

**Вопрос 37. Зачем `--platform=$BUILDPLATFORM` в build-этапе? ●●●**
При кросс-сборке (например, armv7 на amd64-хосте) без этого флага весь build-этап
исполнялся бы под QEMU-эмуляцией — медленно, а maven-образа под armv7 вообще нет.
Флаг говорит: «build-этап всегда выполняй нативно на архитектуре хоста сборки».
Fat-jar платформо-независим — результат годится для любой архитектуры; под QEMU
остаются только лёгкие runtime-этапы (например, `apt-get install` для armv7).

**Вопрос 38. Почему armv7 — отдельный Dockerfile на Debian? ●●●**
Eclipse Temurin (как и большинство вендоров) не публикует armv7-образов JDK 21.
Решение — `debian:13-slim` + пакет `openjdk-21-jre-headless` (armhf), существование
которого проверено по индексу пакетов Debian. Урок: архитектурные ограничения
экосистемы нужно проверять по первоисточникам, а не предполагать.

**Вопрос 39. Почему healthcheck на Java, а не curl? ●●○**
В temurin-образе нет curl/wget. Ставить их ради healthcheck — лишние пакеты в
рантайме. Вместо этого отдельный `main()` (`HealthCheck`): `HttpClient` → GET
`/api/health` → exit 0/1. Docker выполняет `java -cp app.jar ...HealthCheck`
каждые 30 секунд.

**Вопрос 40. Что такое non-root контейнер и зачем? ●○○**
Процесс приложения запускается под непривилегированным пользователем `app`
(`USER app`), а не root. Если приложение скомпрометируют, атакующий не получит root
в контейнере — меньше риск эскалации на хост.

**Вопрос 41. Multi-arch: как собрать под 3 архитектуры без registry? ●●●**
Manifest-list (один тег на 3 платформы) живёт только в registry — в локальный Docker
его не загрузить. Без registry: per-platform tar через buildx (`-o type=docker,
dest=...`), каждый со своим `RepoTags` (`genpass:1.0`), и импорт нужного на NAS.
Важный урок: без тега в tar после `docker load` образ будет `<none>`, и docker-compose
с `image: genpass:1.0` не найдёт его — тег проверяется в манифесте tar.

**Вопрос 42. Что входит в docker-compose и почему такие настройки? ●○**
`restart: unless-stopped` (переживает перезагрузку NAS), порт хоста 8088 → 8080
(8080 на DSM часто занят), env `PORT=8080`, healthcheck тем же Java-классом.
Без устаревшего ключа `version:` (compose v2+).

## 9. Процесс и git

**Вопрос 43. Как организована работа над проектом? ●●○**
Проект вёл по плану из 6 этапов (M0–M5): чистая базовая линия сборки → ядро с
тестами → веб-слой → Docker → деплой-инструкции → приёмка/хардненинг. Каждый этап —
отдельный коммит с зелёной сборкой; между этапами — подтверждение пользователя.
Test-first: сначала тесты (падают «класс не найден»), потом реализация до зелёного.
Финал: независимое ревью свежим ревьюером (0 критичных), исправление минорных
замечаний, тег `v1.0.0`.

**Вопрос 44. Что такое git worktree и зачем он был? ●●○**
`git worktree add` — второй рабочий каталог того же репозитория на отдельной ветке.
Позволяет вести разработку, не трогая `master` (в `master` — стабильная база), и
переключаться между задачами без `stash`. По согласованию работу перенесли на
`master` напрямую — ветка смержена, worktree удалён.

**Вопрос 45. Как обрабатывалось замечание пользователя? ●○○**
Замечание «не везде тёмная тема»: интерпретировано как требование полной тёмной темы
(панель результата была тёмной, страница — светлой). Изменение палитры с сохранением
контрастов ≥4.5:1, проверка computed-стилей в headless Chrome, пересборка артефактов,
обновление документации. Пользователь подтвердил приёмку.

## 10. «Что бы ты улучшил?» (важно для Middle)

- **HTTPS**: приложение отдаёт HTTP; за reverse-proxy на NAS стоит TLS. В проде —
  termination на прокси или встроенный TLS.
- **Rate limiting**: эндпоинты генерации не имеют ограничения частоты; для
  state-less LAN-инструмента риск мал, но лимит на клиента — дешёвая защита.
- **CI/CD**: сборка и 59 тестов сейчас гоняются локально/в build-этапе Docker;
  в идеале — GitHub Actions (mvn verify + docker build на каждый PR) и автоматическая
  публикация образов в registry при теге.
- **Наблюдаемость без логов секретов**: метрики (количество запросов, latency,
  ошибки) через endpoint `/metrics` в формате Prometheus — логировать нельзя, а
  метрики можно.
- **Graceful shutdown**: добавить `awaitTermination` с таймаутом и повторный `stop`,
  чтобы гарантированно завершить in-flight запросы.
- **Тест на «долгую» статистику** в CI отдельным профилем (100k генераций ~0.5 с —
  уже быстро, но можно вынести).
- **Зависимости**: зафиксировать версии и добавить проверку CVE (OWASP Dependency
  Check / Dependabot).
- **UI**: добавить `prefers-color-scheme` поддержку, если понадобится светлая тема;
  сейчас тема одна — тёмная (решение пользователя).
