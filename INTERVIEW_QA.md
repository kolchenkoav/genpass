# genpass — вопросы и ответы для собеседования
## Java Developer (Junior → Middle)

Подготовка по реальному пет-проекту: **genpass** — state-less офлайн-генератор паролей /
passphrase / PIN (Java 21, Maven, встроенный JDK HttpServer, ванильный JS-UI, Docker
multi-arch amd64/arm64/armv7 для деплоя на Synology NAS).

Метки сложности: ●○○ — Junior, ●●○ — уверенный Junior/Middle, ●●● — Middle+ (каверзные).

## 1. Архитектура и дизайн

**Вопрос 1. Расскажи про архитектуру проекта. ●○○**
Два слоя с односторонней зависимостью:
- `org.example.genpass.core` — ядро генерации: `CryptoRandom`, `CharGroups`, records-опции
  (`PasswordOptions`, `PassphraseOptions`, `PinOptions`), генераторы (`PasswordGenerator`,
  `PassphraseGenerator`, `PinGenerator`), `Wordlist`, `StrengthEstimator`.
- `org.example.genpass.web` — HTTP: `WebServer`, `ApiHandlers`, `StaticHandler`,
  `SecurityHeaders`, `HealthCheck`.

Ключевое правило: зависимости направлены только внутрь — `web → core`, а ядро не знает
про HTTP и Jackson (проверяется поиском импортов). Благодаря этому ядро тестируется
чистыми unit-тестами без поднятия сервера, а веб-слой — тонкий: разобрал JSON →
вызвал ядро → сериализовал ответ.

**Вопрос 2. Почему не Spring Boot? ●●○**
Spring отсутствовал в зависимостях и избыточен: приложение state-less, один процесс,
три POST-эндпоинта и статика. Встроенный `jdk.httpserver` даёт ноль новых зависимостей
(меньше CVE-поверхность и размер образа), многопоточность — через `ExecutorService`.
Это осознанный трейд-офф: больше ручного кода (роутинг, ошибки), но для LAN-инструмента
это приемлемо и проще аудировать. На собеседовании важно показать, что выбор — решение,
а не незнание Spring.

**Вопрос 3. Зачем DTO-records, а не мапы? ●○○**
Типобезопасность и самодокументируемость: `record PasswordRequest(int length, boolean
lowercase, ...)` задаёт контракт API. Неизвестное поле в JSON → 400 автоматически
(Jackson по умолчанию `FAIL_ON_UNKNOWN_PROPERTIES`), опечатка в ключе не пройдёт молча,
как с `Map<String, Object>`.

**Вопрос 4. Почему validation в конструкторах records, а не в сервисах? ●○○**
Инварианты объекта должны держаться самим объектом: `PasswordOptions` с длиной 3
просто не может существовать — компактный конструктор бросит `IllegalArgumentException`
(границы 4–128, хотя бы один набор). Тогда ни генератору, ни оценщику энтропии не нужно
повторять проверки, и «битый» объект не просочится вглубь. Валидируем на границе системы.

## 2. Java Core

**Вопрос 5. Что такое record? Чем отличается от класса? ●○○**
Короткая неизменяемая модель данных: автоматически получает конструктор со всеми полями,
`equals`/`hashCode`/`toString` и аксессоры. В проекте — опции генерации и DTO.
Ключевое: поля `final`, класс финальный — неизменяемость «из коробки», что важно для
объектов-конфигураций. Если нужна валидация — компактный конструктор (без списка
параметров, с ними — тело).

**Вопрос 6. Почему почти все классы final, а конструкторы приватные? ●○○**
`final`-класс запрещает наследование — для утилитных классов (например, `CharGroups`,
`StrengthEstimator`) наследование бессмысленно и опасно. Приватный конструктор +
`static`-методы — паттерн «утилита» (как `Collections`). Неизменяемость упрощает
рассуждения о потокобезопасности: объект без состояния или с `final`-полями безопасно
шарить между потоками.

**Вопрос 7. Зачем `List.copyOf` в `Wordlist`? ●○○**
Возвращает неизменяемую копию: после загрузки словарь не может быть изменён извне
(защитное копирование). Словарь грузится один раз и шарится между всеми запросами —
неизменяемость делает это безопасным без синхронизации на чтении.

**Вопрос 8. Где в проекте switch-expression? ●○○**
`StaticHandler.resourceFor()`: маппинг пути на ресурс через `switch`-expression
(`case "/" -> "/web/index.html"; ...`). Без `break`, без проваливаний, выражение —
компактнее и безопаснее старого `switch`-statement.

**Вопрос 9. try-with-resources: где используется и почему это важно? ●○○**
Везде, где открываются ресурсы: чтение словаря (`BufferedReader` из `InputStream`),
тело ответа (`OutputStream`), чтение файла в `StaticHandler`. Гарантирует `close()`
даже при исключении. Ручной `close()` в `finally` остался только у `HttpExchange` —
это не `AutoCloseable`-паттерн сервера, там свой жизненный цикл.

## 3. Многопоточность

**Вопрос 10. Как устроен пул потоков и graceful shutdown? ●●○**
`WebServer` создаёт `HttpServer` с `ExecutorService.newFixedThreadPool(4)` — JDK-сервер
сам не плодит поток на запрос, а берёт из пула (ограничение ресурсов). Остановка:
shutdown-hook в `App.main` вызывает `server.stop(1)` (до 1 секунды на завершение
in-flight запросов) и `executor.shutdown()` — потокобезопасная остановка без
«висящих» запросов.

**Вопрос 11. Почему shared `SecureRandom` безопасен, а shared `Random` — нет? ●○○**
`SecureRandom` потокобезопасен (внутренняя синхронизация), `java.util.Random` тоже
атомарен на seed, но дело не в этом: `Random` — не криптостойкий (линейный конгруэнтный,
предсказуем по нескольким значениям). В проекте единый `CryptoRandom.INSTANCE` —
«один экземпляр SecureRandom на JVM» (требование спеки проекта).

**Вопрос 12. Как устроен ленивый синглтон `Wordlist.getDefault()`? ●●○**
Double-checked locking: `volatile`-поле + `synchronized`-блок с повторной проверкой —
дорогая загрузка (чтение 1296 строк из jar) выполняется один раз, параллельные потоки
не блокируются на чтении после инициализации. `volatile` гарантирует видимость
полностью сконструированного объекта.

**Вопрос 13. Утечки: на что обращать внимание с HttpServer? ●●○**
Каждый `HttpExchange` обязан быть закрыт (`exchange.close()` в `finally`) — иначе
утечка дескрипторов и «висящие» соединения. Это классическая болевая точка ручного
HTTP-слоя, и в проекте закрытие вынесено в `finally` во всех хендлерах.

**Вопрос 14. Почему пул из 4 потоков, а не «по потоку на запрос»? ●●○**
«Поток на запрос» не масштабируется: при 100 параллельных запросах — 100 потоков и
переключение контекста. Фиксированный пул ограничивает потребление и даёт
предсказуемость; для генератора (задача на микросекунды, без I/O-блокировок) 4 потока
с запасом. Для CPU-bound задач оптимален пул ~= числу ядер (можно было взять
`availableProcessors()`).

## 4. Безопасность и криптография

**Вопрос 15. Почему `SecureRandom.nextInt(bound)`, а не `random.nextInt() % bound`? ●●○**
`% bound` даёт **modulo bias**: при `bound`, не делящем 2³¹, младшие значения
встречаются чаще (например, `% 10` на 2³¹ значениях: остатки 0–7 встречаются чаще,
чем 8–9). Для генератора паролей это измеримое смещение в распределении — атакующий
получает преимущество. `nextInt(bound)` внутри JDK делает rejection sampling —
равномерно.

**Вопрос 16. Что такое энтропия пароля и как она считается? ●●○**
Энтропия = `log2(размер пространства)`. Для случайного пароля: `длина × log2(размер
алфавита)`. Примеры из проекта: 8 строчных букв = `8 × log2(26)` ≈ 37.6 бит;
passphrase из 5 слов словаря в 1296 слов = `5 × log2(1296)` ≈ 51.7 бит — длинная
фраза из словаря сильнее короткого «сложного» пароля. Словесные метки: <40 слабый,
40–59 средний, 60–79 сильный, ≥80 очень сильный. Плюс справочное время перебора при
10¹⁰ попыток/сек: `2^биты / 10^10` секунд.

**Вопрос 17. Зачем в оценке энтропии учитывать `excludeAmbiguous`? ●●○**
Флаг исключает символы `I l 1 O 0` — они неоднозначны при вводе. Но исключение
**уменьшает алфавит**: полный пул из 4 наборов — 89 символов, после исключения — 84
(из lower уходит `l`, из upper — `I`,`O`, из digits — `1`,`0`; `|` в спецнаборе проекта
нет, поэтому фильтр для него — no-op). Если оценку не корректировать, она будет
завышенной — «честность оценки» была отдельным требованием.

**Вопрос 18. Почему passphrase с цифрой добавляет ровно ~3.32 бита? ●●○**
`log2(10) ≈ 3.3219` — цифра добавляет один символ из десяти возможных. В проекте
осознанно упростили: цифра добавляется в **конец** одного случайного слова, а не в
произвольную позицию — реализация проще, а оценка остаётся консервативной (не
завышенной: позиция цифры не увеличивает пространство, но и не уменьшает).

**Вопрос 19. Что дают HTTP-заголовки безопасности? ●●○**
- `Cache-Control: no-store` — пароль не должен осесть в кэше браузера/прокси
  (на статике — `no-cache`: переvalidate, но кэшировать можно).
- CSP `default-src 'none'; script-src 'self'; ...` — даже при XSS браузер не выполнит
  инлайн-скрипт или внешний ресурс; поэтому в UI **запрещены инлайн-скрипты** — JS
  только в отдельном `app.js`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (не светим URL с
  паролями в реферрере), `X-Frame-Options: DENY` (защита от clickjacking).

**Вопрос 20. Почему slf4j-nop — это «фича безопасности»? ●●●**
В pom подключён `slf4j-nop` — реализация, которая ничего не пишет. Для приложения,
генерирующего секреты, это гарантия: даже если какая-то библиотека начнёт логировать,
вывод будет пустым. Плюс код сам не логирует результаты: в stdout — только строка
старта. Логирование пароля — это утечка секрета в систему, из которой его потом
невозможно «удалить».

**Вопрос 21. Что значит state-less и зачем это? ●○○**
Приложение не хранит состояние: нет БД, файлов, сессий. Каждый запрос независим.
Следствия: контейнер можно перезапускать/масштабировать без потерь; нечего красть
из «хранилища паролей» — их там нет; поверхностная площадь атаки минимальна.

## 5. HTTP, JSON, веб-слой

**Вопрос 22. Какие эндпоинты и какие статусы? ●○○**
`GET /api/health` (healthcheck), `POST /api/password|passphrase|pin`, статика `/`,
`/app.js`, `/style.css`. Ошибки: 400 — невалидные параметры/JSON, 404 — неизвестный
путь, 405 + заголовок `Allow` — неверный метод, 413 — тело больше 64 КБ.

**Вопрос 23. Почему 405 требует заголовка Allow? ●○**
`Allow` сообщает клиенту, какие методы разрешены на ресурсе (`Allow: POST`) — это
часть HTTP-контракта, клиент может сразу повторить правильным методом.

**Вопрос 24. Как ограничили размер тела и зачем? ●●○**
Чтение тела в буфер с проверкой лимита 64 КБ по ходу чтения → 413. Без лимита
злоумышленник может исчерпать память JVM одним запросом (DoS). Проверка до парсинга
JSON — важно: парсить гигантское тело нельзя.

**Вопрос 25. Зачем path-guard'ы, если контексты уже зарегистрированы? ●●●**
`HttpServer` матчит контекст по **префиксу**: `/api/password` поймает и
`/api/password/x`. Поэтому в хендлере сверяется точный путь, и «хвост» получает 404.
Второй нюанс — порядок проверок: сначала путь, потом метод, иначе `GET /api/password/x`
вернул бы 405 вместо 404 (это был реальный баг, пойманный тестами).

**Вопрос 26. Строгая коэрсия JSON: что это и зачем? ●●○**
Jackson по умолчанию «добрый»: `{"length": "20"}` сконвертирует строку в число,
`{"length": 4.9}` — **молча усечёт** до 4. Для API, генерирующего секреты, это
неприемлемо: отключены `ACCEPT_FLOAT_AS_INT` и `ALLOW_COERCION_OF_SCALARS` → оба
запроса получают 400. Тип контракта должен соблюдаться строго.

**Вопрос 27. Как устроена статика без фреймворков? ●○**
`StaticHandler` отдаёт ровно три файла из classpath (`/web/index.html` и т.д.) с
правильным `Content-Type` и `charset=UTF-8`; любой другой путь — 404. Никакого
листинга каталогов (в classpath его и не может быть «случайно»). HEAD поддерживается
(ответ без тела) — часть HTTP-контракта.

**Вопрос 28. Почему JSON в UTF-8 и с charset в Content-Type? ●○**
JSON по спецификации — UTF-8, но явный `charset=UTF-8` убирает неоднозначность для
клиентов; спецсимволы паролей (`!@#$%^&*()`) и русские метки («средний») должны
корректно экранироваться/декодироваться.

**Вопрос 29. Как работает UI и почему он «офлайн»? ●○○**
Ванильные HTML/CSS/JS, три вкладки-режима, fetch на свой же origin с
`cache: 'no-store'`. Копирование: `navigator.clipboard` (требует secure context —
HTTPS) с fallback на `document.execCommand('copy')` для HTTP в LAN. Никаких CDN,
шрифтов, телеметрии — всё внутри jar. CSP это ещё и подкрепляет: `connect-src 'self'`.

## 6. Тестирование

**Вопрос 30. Какие виды тестов и почему такая связка? ●○○**
Unit (TestNG, 42 теста) — ядро: границы валидации, принадлежность алфавиту, гарантия
покрытия наборов, статистика, энтропия. Интеграционные (rest-assured, 17 тестов) —
веб: старт реального сервера на свободном порту (`ServerSocket(0)`), статусы,
заголовки, схема ответов. TestNG выбран, потому что был в зависимостях шаблона —
но это полноценный фреймворк с suite-файлами (`testNG.xml`), аннотациями
`@BeforeSuite`/`@AfterSuite`.

**Вопрос 31. Как тестировать случайность? ●●●**
Никак «в лоб»: нельзя засидить `SecureRandom` (это сломало бы смысл теста и требует
API для инъекции). Вместо этого — статистика: 100 000 генераций, подсчёт частот,
проверка, что каждая частота в допуске ±20% от равномерной. При 100k испытаний и 26
символах отклонение на 20% — это ~12 сигм: ложное срабатывание практически невозможно,
а реальное смещение генератора тест поймает. Плюс «гарантия покрытия» проверяется
детерминированно: 1000 генераций длины 4 со всеми 4 наборами — в каждой должен быть
символ каждого набора (это инвариант алгоритма, не статистика).

**Вопрос 32. Почему в статистическом тесте длина 4, а не 1? ●●○**
Спека запрещает пароли короче 4 (`PasswordOptions` бросит исключение), поэтому
измерить «символ длины 1» нельзя. Решение: генерировать длину 4 и считать
распределение **первого символа** — распределение то же самое (равномерный выбор),
а валидация не нарушена. Хороший пример, как тест подстраивается под контракт.

**Вопрос 33. Как тестируется энтропия? ●○**
Точечными значениями с допуском: `entropyBits(8 строчных) == 37.60 ± 0.01`.
Интересный кейс: в спеке было «5 слов из 1296 ≈ 51.65 бит», но `5 × log2(1296) =
51.699` — спека была математически неверна, тест писался по правильному значению,
а спека поправлена (это пример, как тесты вскрывают ошибки документации).

**Вопрос 34. Какие негативные сценарии покрыты? ●○**
400: длина 3, 129, 100 слов, все наборы выключены, битый JSON, неизвестное поле,
строка/дробь в числе; 404: неизвестный путь и «хвост» известного; 405 с Allow;
413: тело 70 КБ; 404 API несёт `no-store`.

**Вопрос 35. Что проверяют интеграционные тесты, кроме статусов? ●●○**
Схему ответа (`result`, `entropyBits`, `strength`, `crackTime`), семантику опций
(ровно одна цифра в passphrase, ни одного ведущего нуля в PIN), заголовки
безопасности на ответах. Например, тест парсит passphrase, считает слова и проверяет
капитализацию — это проверка поведения, а не «что сервер ответил 200».

## 7. Реальные баги и уроки (кейсы для рассказа)

> Это самое ценное на собеседовании: пересказ чужого опыта никого не впечатляет,
> а вот «я нашёл такой баг, диагностировал так, чинил так, проверял так» — показывает,
> как ты думаешь. Каждый кейс ниже — реальная история проекта с полным циклом:
> симптом → обнаружение → диагностика → корень → фикс → проверка → что могут
> спросить вдогонку.

---

### Кейс 1. «Сервер молча рвёт соединение» (NoHttpResponse) ●●●
**Самый показательный кейс: диагностика «сервер не отвечает», когда сервер жив.**

**Симптом.** После первой реализации веб-слоя упали 6 из 56 интеграционных тестов:
`GET /`, `GET /app.js`, `GET /style.css`, `HEAD /` — клиент получал
`NoHttpResponse ... failed to respond` (rest-assured) — соединение закрыто без ответа.
При этом `POST /api/password|passphrase|pin` и `GET /api/health` работали идеально.

**Обнаружение.** Падали только GET-запросы на статику; API — нет. Это сразу сузило
круг: проблема в ветке кода, общей для всех статических ответов.

**Диагностика по шагам (важно показать на интервью):**
1. `curl -s -o /dev/null -w "%{http_code}"` на каждый эндпоинт → `GET /` = **000**
   (curl: соединение закрыто без HTTP-ответа), `/api/health` = 200.
2. Ключевой эксперимент — бинарный поиск внутри хендлера: `GET /missing` (404) =
   **404 работает**, `GET /` (200 с телом) = **000**. Значит, ломается именно ветка
   «200 + тело», а ветка «ошибка без тела» — живая.
3. Чтение кода `StaticHandler` против данных эксперимента. Нашёл несоответствие:
   карта `CONTENT_TYPES` ключуется **именами файлов** (`"index.html"`, `"app.js"`),
   а маппинг пути возвращает **ресурсные пути** (`"/web/index.html"`, `"/web/app.js"`).
   `CONTENT_TYPES.get("/web/index.html")` → `null`.
4. Дальше — цепочка: `responseHeaders.set("Content-Type", null)` → внутри
   `com.sun.net.httpserver.Headers.set` стоит `Objects.requireNonNull(value)` →
   **NullPointerException**.
5. Почему «молча»? NPE — `RuntimeException`, он не ловился `catch (IOException)` в
   хендлере. `HttpServer` при необработанном исключении хендлера **не пишет в лог и
   не отдаёт 500** — он просто закрывает соединение. Отсюда `000`/`NoHttpResponse`,
   а не внятная ошибка.

**Корень.** Рассогласование ключей мапы + пустой `catch (IOException)` + поведение
`HttpServer`: три фактора, каждый по отдельности безобиден, вместе — «сервер молчит».

**Фикс.** Ключи карты приведены к ресурсным путям (`"/web/index.html"` → тип).
Одна строка данных, но диагностика заняла всё остальное время.

**Проверка/регрессия.** Пересборка → curl-смоук всей статики (200, HEAD 200) →
полный `mvn clean verify` — 56/56 зелёные. Смоук реальными запросами остался в
арсенале как обязательный шаг.

**Что могут спросить вдогонку:**
- «Почему NPE, а не 500?» — см. шаг 5: `HttpServer` не перехватывает исключения
  хендлера как HTTP-ошибку.
- «Как бы ты защитился от такого класса багов?» — не глотать исключения молча
  (минимум — логировать с уровнем error; у нас осознанно `slf4j-nop`, поэтому
  аккуратность вдвойне важна), и покрыть статику тестами на Content-Type —
  тест `staticAssetsServedWithTypes` теперь проверяет `contentType(...)`.
- «Почему браузер бы это заметил, а ты — нет?» — браузер не отрисовал бы стили/JS,
  UI был бы «голым»; автотесты на статусы без проверки заголовков это пропускают.

**Урок.** (1) Пустой `catch` — антипаттерн: он превращает любую ошибку в «чёрный ящик».
(2) Эксперимент «404 работает / 200 нет» — образец бинарного поиска причины.
(3) Знай поведение платформы: `HttpServer` молча рвёт соединение при исключении.

### Кейс 2. «Все вкладки видны одновременно» ●●○
**Кейс о том, что фронтенд-баг — тоже баг, и о разнице «DOM есть» и «элемент виден».**

**Симптом.** Пользователь открыл страницу и сообщил: на экране сразу **все три формы**
(Пароль, Passphrase, PIN), хотя по дизайну видна только активная. Наш браузерный
смоук этого не поймал.

**Корень.** Каскадность CSS. У браузера есть встроенное (UA) правило:
`[hidden] { display: none }`. Но авторские стили всегда сильнее UA-стилей — это
**происхождение (origin)**, а не специфичность: даже `[hidden]` с высокой
специфичностью проиграет любому авторскому `display`. В проекте:
```css
.panel { display: flex; ... }   /* авторское правило */
<form class="panel" hidden>     /* атрибут hidden игнорируется: display:flex победил */
```
Атрибут `hidden` — не «свойство», а соглашение, которое держится только на том, что
никто не задал `display` явно.

**Почему смоук пропустил.** Мой первый CDP-смоук кликал кнопки и читал `textContent`
результата — всё это работает и у «невидимо-видимых» панелей: клик по кнопке внутри
`display:flex`-панели успешен, текст читается. Смоук проверял **поведение**, но не
**представление**. Классика: тест зелёный, а пользователь видит сломанный экран.

**Фикс.**
```css
[hidden] { display: none !important; }
```
`!important` в авторской таблице перебивает обычные авторские правила — теперь
атрибут работает всегда.

**Проверка/регрессия.** Новый CDP-скрипт проверяет **computed style**:
```js
getComputedStyle(panel).display  // ожидаем: password=flex, passphrase=none, pin=none
```
При загрузке и после переключения каждой вкладки — все четыре сценария зелёные,
плюс повторный полный смоук генерации.

**Что могут спросить вдогонку:**
- «Как браузер решает, какое правило победит?» — три уровня: происхождение
  (UA < пользователь < автор; `!important` инвертирует порядок внутри уровня),
  специфичность (id > класс > элемент), порядок объявления.
- «Какие ещё способы скрыть элемент и чем они отличаются?» — `hidden`,
  `display:none` (выпадает из потока, невидим для скринридеров-в-потоке),
  `visibility:hidden` (место занято), `opacity:0` (кликабелен!), `position:absolute`
  за экран, `content-visibility`. Для вкладок важен и `aria-selected`/`role=tab`.

**Урок.** (1) Тест должен проверять то, что видит пользователь, — для UI это
computed styles, а не только DOM. (2) Не спорить с пользователем: «у меня тесты
зелёные» ≠ «у тебя работает». (3) `hidden` + явный `display` — грабли, которые
стоит знать любому, кто пишет CSS.

### Кейс 3. rest-assured: Float вместо Double ●●○
**Кейс о том, что HTTP-клиент сам решает, как парсить JSON-числа.**

**Симптом.** Два теста упали на **валидных** ответах сервера:
- `body("entropyBits", greaterThan(0d))` — «Expected: a value greater than <0.0>,
  Actual: <127.84635F>»;
- `body("entropyBits", closeTo(55.02, 0.1))` — «Actual: <55.02118F>».

Число верное (127.85 > 0, 55.02118 ≈ 55.02 ± 0.1), а тест красный.

**Корень.** Rest-assured (через Groovy JsonPath) по умолчанию парсит десятичные
JSON-числа в **`Float`** (суффикс `F` в выводе — улика). А матчеры Hamcrest,
созданные через `greaterThan(0d)` / `closeTo(55.02, 0.1)`, типизированы под
**`Double`**. Типизированный матчер против `Float`-значения не срабатывает —
отсюда «не совпало» на заведомо верном числе. Плюс у `Float` своя точность:
55.02118F ≈ 55.02117919921875 — для строгих допусков это тоже источник сюрпризов.

**Фикс.** Настроить парсер глобально в `@BeforeSuite`:
```java
RestAssured.config = RestAssured.config().jsonConfig(
    JsonConfig.jsonConfig()
        .numberReturnType(JsonPathConfig.NumberReturnType.DOUBLE));
```
После этого десятичные числа приходят как `Double`, и матчеры работают как ожидалось.

**Что могут спросить вдогонку:**
- «А какие ещё варианты numberReturnType есть?» — `FLOAT` (по умолчанию), `DOUBLE`,
  `BIG_DECIMAL` (для денег/точных расчётов — никогда не используй float/double).
- «Почему в JSON нет типа числа?» — JSON-спецификация: number — одно семейство;
  тип выбирает парсер. Отсюда же классические грабли «JSON.parse вернёт double».
- «Было ли это багом сервера?» — нет; сервер честно вернул `55.02117810931048`.
  Баг был в ожиданиях теста. Важный навык — отличать «сломан код» от «сломан тест».

**Урок.** Прежде чем писать матчер на JSON-число, узнай, как твой клиент его парсит;
суффикс типа в сообщении об ошибке (`55.02118F`) — это подсказка от фреймворка.

### Кейс 4. Порядок проверок: 405 вместо 404 ●○○
**Кейс о семантике REST и подводном камне префикс-матчинга HttpServer.**

**Симптом.** Тест `unknownApiPathReturns404`:
`GET /api/password/x` → ожидали 404, получили **405** (и это при том, что
`GET /api/unknown` честно давал 404).

**Корень.** Два механизма:
1. `HttpServer.createContext("/api/password", ...)` матчит **по префиксу**: запрос
   `/api/password/x` попадает в наш хендлер (это не баг, а документированное
   поведение longest-prefix matching). Поэтому внутри хендлера нужен path-guard —
   сверка точного пути.
2. В хендлере проверки стояли в неверном порядке: сначала «метод не POST? → 405»,
   потом «путь не тот? → 404». Для `/api/password/x` метод GET → 405 «выстреливал»
   раньше, чем хендлер успевал понять, что ресурса вообще нет.

**Семантика.** 405 = «ресурс есть, но метод не поддерживается»; 404 = «ресурса нет».
Для несуществующего пути правильный ответ — 404 **независимо от метода**: клиент
спрашивает про другой ресурс, а не про метод этого.

**Фикс.** Перестановка: сначала точный путь (`404`), потом метод (`405` + `Allow`),
в обоих хендлерах (и POST-эндпоинты, и health).

**Проверка.** Тот же тест стал зелёным; отдельные тесты на 405 (POST на
`/api/health` с `Allow: GET`, GET на `/api/password` с `Allow: POST`) подтвердили,
что семантика 405 сохранилась для существующих путей.

**Что могут спросить вдогонку:**
- «Чем 404 отличается от 405 и 410?» — 404 нет ресурса; 405 метод не разрешён
  (+ обязательный `Allow`); 410 ресурс был и удалён навсегда.
- «Почему нельзя просто зарегистрировать контекст на каждый путь отдельно?» —
  можно, но префикс-матчинг всё равно потребует гарда для «хвостов»; сверка пути
  в одном хендлере проще и явнее.

**Урок.** Порядок проверок в хендлере — это часть контракта API, и его фиксируют
тестами. Сначала — идентификация ресурса, потом — операция над ним.

### Кейс 5. Спека против математики ●○○
**Кейс о том, что тесты — источник правды, а документация ошибается.**

**Симптом.** В плане проекта было написано: «5 слов из словаря 1296 ≈ **51.65**
бит». При написании теста пересчитали: `5 × log2(1296) = 5 × 10.339850 = 51.6992`
≈ **51.70** бит. Расхождение 0.05 — на первый взгляд мелочь, но тест с допуском
±0.01 не мог бы быть зелёным ни с одним из значений одновременно.

**Разбор.** `51.65` — вероятно, результат округления в уме или опечатка плана.
Математика однозначна: энтропия словаря `log2(N)` — ровно 10.33985 для N=1296,
умножение на 5 не даёт 51.65. Тест написан по **формуле**, а не по числу из спеки.

**Решение.** Тест зафиксировал `51.70 ± 0.01` (и `55.02` с цифрой — +log2(10)).
Спека поправлена: значение заменено на верное с комментарием, почему. Правка
документации по следам теста — нормальный процесс, а не «подгонка».

**Что могут спросить вдогонку:**
- «А если бы спека была правой, а формула — нет?» — тогда вопрос к формуле:
  log2(1296) проверяется напрямую; эмпирически: 2^51.65 и 2^51.70 — оба «около»
  1296^5, но точное значение даёт только логарифм. Числа в тестах должны выводиться,
  а не угадываться.
- «Где ещё в проекте проверялась математика?» — энтропия PIN с `noLeadingZero`:
  точная формула `log2(9) + (n−1)·log2(10)` (первая цифра — 1..9, остальные —
  0..9), а не наивное `n·log2(10)`; и 8 строчных = 37.60 бит — точечные значения с
  допуском ±0.01 в unit-тестах.

**Урок.** Тесты фиксируют **поведение**, а не числа из документации. Нашёл
расхождение — пересчитай и поправь документ, не подгоняй тест под опечатку.

### Кейс 6. Docker: Java 17-образ не запустит jar 21-го класса ●●○
**Кейс о том, что «собралось локально» ≠ «заработает в контейнере».**

**Симптом (потенциальный, пойман до деплоя).** Проект по решению пользователя
переведён с Java 17 на Java 21 (`pom.xml`: source/target 21). Плановая
контейнеризация была написана под Java 17: builder `maven:3.9-eclipse-temurin-17`,
runtime `eclipse-temurin:17-jre`. Запуск jar, скомпилированного под 21, на JRE 17
упал бы мгновенно: `UnsupportedClassVersionError` — классы имеют major version **65**
(Java 21), а JVM 17 понимает максимум **55**.

**Почему это классика.** Версии компилятора и рантайма — часть контракта поставки.
Локально разработчик гоняет JDK 21 и «всё работает»; в контейнере — другой JDK, и
проект падает на первом же классе. Отсюда правило: рантайм-образ обязан собираться
из той же мажорной версии, что и артефакт (или артефакт должен быть собран с
`--release 17`, если рантайм 17 — осознанный выбор).

**Вторая часть кейса — armv7.** План предусматривал armv7-образ на Debian 12
(bookworm) с `openjdk-17-jre-headless`. Под Java 21 выяснилось: **в bookworm пакета
`openjdk-21` нет** (там 17), Temurin armv7-образов не публикует вовсе. Проверка:
- `packages.debian.org` закрыт от скрейпинга (JS-челлендж) — не источник;
- авторитетный источник — сам индекс пакетов:
  `curl deb.debian.org/debian/dists/trixie/main/binary-armhf/Packages.gz` →
  `Package: openjdk-21-jre-headless`, версия `21.0.11+10-1~deb13u2`, ~165 МБ
  установленного. Вывод: Debian **13 (trixie)** содержит нужный пакет для armhf.

**Фикс.** `Dockerfile`: builder и runtime → temurin-21. `Dockerfile.armv7`:
`debian:13-slim` + `openjdk-21-jre-headless`. План (разделы 8.1–8.2) обновлён —
актуализация документации под принятое решение.

**Проверка.** Недостаточно «собралось»: arm64- и armv7-образы **запущены под
эмуляцией QEMU** на amd64-хосте (`docker run --platform linux/arm/v7`), `/api/health`
→ 200, в логах — строка запуска 1.0.0. Кросс-архитектурный прогон поймал бы и
битые нативные зависимости (их нет — fat-jar чистый Java), и неверный рантайм.

**Что могут спросить вдогонку:**
- «Что такое class file version?» — байткод-версия класса: Java 8 = 52, 11 = 55,
  17 = 61, 21 = 65. JVM запускает классы с версией ≤ своей.
- «Чем грозит рассинхрон ещё?» — API-методы: код, собранный под 21, может звать
  API, отсутствующие в 17 (например, `String.repeat` — есть с 11, а `SequencedMap`
  — только с 21). `UnsupportedClassVersionError` — лишь первая, самая грубая ошибка.
- «Почему maven-образ собирается нативно при кросс-сборке?» —
  `--platform=$BUILDPLATFORM`: Maven (и тесты!) исполняются на архитектуре хоста,
  а не под QEMU; fat-jar платформо-независим, поэтому результат годится для всех
  трёх архитектур. Под QEMU остаются только лёгкие runtime-шаги вроде `apt-get`.

**Урок.** (1) Версия JDK — сквозной контракт: pom → Dockerfile → рантайм → тесты в
CI. (2) Проверять существование пакетов по первоисточнику (индекс репозитория), а
не по догадкам или заблокированным страницам. (3) Кросс-платформенный артефакт
проверяется запуском под целевой архитектурой, пусть и через эмуляцию.

### Бонус-кейсы из разработки (коротко, но тоже годятся в рассказ)

**Бонус 1. Три «бага», которые оказались багами тестов.** В M1 упали три теста,
и все три — из-за неверных ожиданий в самих тестах, а не в коде:
- длина пароля 1 невалидна по спеке (минимум 4) — статистический тест переписан
  на «первый символ генераций длины 4» (распределение то же);
- длина passphrase с пустым разделителем — не «4 × 5 = 20», а сумма длин случайных
  слов из фикстуры (19±) — проверка стала диапазоном;
- `crackTime(40 бит)` = 2⁴⁰/10¹⁰ ≈ 109.95 с ≥ 60 → «~2 мин», а не «~110 сек»
  (человекочитаемая шкала переключается на минуты).

Навык: когда падает тест, первым делом спроси «кто врёт — код или ожидание?» —
и умей доказать (пересчётом, экспериментом), а не гадать.

**Бонус 2. Браузер против data:-URL.** При попытке проверить JS-файл через
`data:text/html,<script src="...">` Chrome заблокировал загрузку: Private Network
Access (страница из «публичного» контекста не может обращаться в local network).
Не баг приложения, но отличная иллюстрация: современный браузер — это security
boundary со своими правилами, и «почему не работает» иногда надо искать в политиках
браузера, а не в коде.

**Бонус 3. Сеть в WSL.** Windows-процессы не достучались до сервера на
`127.0.0.1` в WSL (и наоборот) — помогло обращение по WSL-IP. Урок: при
интеграционных проверках «клиент и сервер на одной машине» — это ещё не значит
«на одном localhost».

## 8. Docker и деплой

**Вопрос 36. Что даёт multi-stage Dockerfile? ●○○**
Два этапа: `build` (maven-образ, компиляция + тесты) и `runtime` (только JRE + jar).
В рантайм-образ не попадают Maven, исходники и кэш зависимостей — меньше размер и
поверхность атаки. Плюс тесты выполняются на этапе сборки: в образ попадает только
проверенный артефакт.

**Вопрос 37. Зачем `--platform=$BUILDPLATFORM` в build-этапе? ●●●**
При кросс-сборке (например, armv7 на amd64-хосте) без этого флага весь build-этап
исполнялся бы под QEMU-эмуляцией — медленно, а maven-образа под armv7 вообще нет.
Флаг говорит: «build-этап всегда выполняй нативно на архитектуре хоста сборки».
Fat-jar платформо-независим — результат годится для любой архитектуры; под QEMU
остаются только лёгкие runtime-этапы (например, `apt-get install` для armv7).

**Вопрос 38. Почему armv7 — отдельный Dockerfile на Debian? ●●●**
Eclipse Temurin (как и большинство вендоров) не публикует armv7-образов JDK 21.
Решение — `debian:13-slim` + пакет `openjdk-21-jre-headless` (armhf), существование
которого проверено по индексу пакетов Debian. Урок: архитектурные ограничения
экосистемы нужно проверять по первоисточникам, а не предполагать.

**Вопрос 39. Почему healthcheck на Java, а не curl? ●●○**
В temurin-образе нет curl/wget. Ставить их ради healthcheck — лишние пакеты в
рантайме. Вместо этого отдельный `main()` (`HealthCheck`): `HttpClient` → GET
`/api/health` → exit 0/1. Docker выполняет `java -cp app.jar ...HealthCheck`
каждые 30 секунд.

**Вопрос 40. Что такое non-root контейнер и зачем? ●○○**
Процесс приложения запускается под непривилегированным пользователем `app`
(`USER app`), а не root. Если приложение скомпрометируют, атакующий не получит root
в контейнере — меньше риск эскалации на хост.

**Вопрос 41. Multi-arch: как собрать под 3 архитектуры без registry? ●●●**
Manifest-list (один тег на 3 платформы) живёт только в registry — в локальный Docker
его не загрузить. Без registry: per-platform tar через buildx (`-o type=docker,
dest=...`), каждый со своим `RepoTags` (`genpass:1.0`), и импорт нужного на NAS.
Важный урок: без тега в tar после `docker load` образ будет `<none>`, и docker-compose
с `image: genpass:1.0` не найдёт его — тег проверяется в манифесте tar.

**Вопрос 42. Что входит в docker-compose и почему такие настройки? ●○**
`restart: unless-stopped` (переживает перезагрузку NAS), порт хоста 8088 → 8080
(8080 на DSM часто занят), env `PORT=8080`, healthcheck тем же Java-классом.
Без устаревшего ключа `version:` (compose v2+).

## 9. Процесс и git

**Вопрос 43. Как организована работа над проектом? ●●○**
Проект вёл по плану из 6 этапов (M0–M5): чистая базовая линия сборки → ядро с

отдельный коммит с зелёной сборкой; между этапами — подтверждение пользователя.
Test-first: сначала тесты (падают «класс не найден»), потом реализация до зелёного.
Финал: независимое ревью свежим ревьюером (0 критичных), исправление минорных
замечаний, тег `v1.0.0`.

**Вопрос 44. Что такое git worktree и зачем он был? ●●○**
`git worktree add` — второй рабочий каталог того же репозитория на отдельной ветке.
Позволяет вести разработку, не трогая `master` (в `master` — стабильная база), и
переключаться между задачами без `stash`. По согласованию работу перенесли на
`master` напрямую — ветка смержена, worktree удалён.

**Вопрос 45. Как обрабатывалось замечание пользователя? ●○○**
Замечание «не везде тёмная тема»: интерпретировано как требование полной тёмной темы
(панель результата была тёмной, страница — светлой). Изменение палитры с сохранением
контрастов ≥4.5:1, проверка computed-стилей в headless Chrome, пересборка артефактов,
обновление документации. Пользователь подтвердил приёмку.

### 🔴 1. HTTPS / TLS: приложение отдаёт секреты по HTTP

**Проблема.** Приложение генерирует секреты и отдаёт их по открытому HTTP.
В LAN-сценарии (домашний NAS) риск перехвата невысок, но: (а) пароль идёт в открытом
виде, если сеть скомпрометирована; (б) `navigator.clipboard` работает только в
secure context — по HTTP копирование держится на устаревшем fallback
`document.execCommand`; (в) «зашифруй трафик» — первое, что скажет security-ревью.

**Как сделать — два пути с разными трейдоффами:**
1. **TLS на reverse-proxy (рекомендуемый для NAS).** Перед приложением — Caddy /
   nginx / встроенный reverse-proxy DSM (в README проекта уже описан: DSM → Порт
   входа → Обратный прокси → Let's Encrypt). Плюсы: приложение не меняется,
   сертификаты с автообновлением, прокси умеет HTTP/2 и сжатие. Минусы: ещё один
   сервис, который надо поддерживать.
2. **Встроенный TLS.** `com.sun.net.httpserver.HttpsServer` + `SSLContext` из
   keystore. Плюсы: ничего лишнего не нужно. Минусы: **жизненный цикл сертификата**
   на вас: генерация, ротация, перезапуск; самоподписанный сертификат даёт браузерные
   варнинги и не защищает от MITM без доверия клиента; Let's Encrypt в jar не
   встроить. Для пет-проекта честный вывод: встроенный TLS не окупается, прокси —
   правильный слой для этого.

**Дополнительно:** при HTTPS добавить заголовок `Strict-Transport-Security`
(навсегда «только HTTPS») и редирект 80→443 на прокси.

**Что сказать вслух:** «Приложение само по себе не терминирует TLS — это осознанное
решение: сертификаты живут на прокси (DSM reverse proxy + Let's Encrypt), а
приложение остаётся простым HTTP-сервисом за доверенной границей. Если бы сервис
был публичным, я бы добавил HSTS и редирект, а встроенный TLS рассматривал бы только
при отсутствии прокси-слоя».

### 🔴 2. CI/CD: тесты и сборка только на машине разработчика — риск

**Проблема.** `mvn clean verify` и Docker-сборка гоняются вручную; 59 тестов
исполняются в build-этапе Docker, но никто не мешает закоммитить код, который
сломает сборку, — узнаем об этом только локально.

**Как сделать.**
```yaml
# .github/workflows/ci.yml — эскиз
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - run: mvn -B clean verify        # 59 тестов
      - uses: actions/upload-artifact@v4 # surefire-отчёты при падении
  docker:
    needs: test
    if: startsWith(github.ref, 'refs/tags/v')
    steps:
      - uses: docker/setup-buildx-action@v3
      - run: docker buildx build --platform linux/amd64,linux/arm64 -t ... --push .
      # armv7 — отдельным job'ом с Dockerfile.armv7
```
**Трейдоффы.** QEMU-сборка armv7 в CI медленная (минуты) — можно собирать armv7
только на тегах, а amd64/arm64 — на каждом PR. Публикация образов требует секретов
registry — хранить в GitHub Secrets, не в репозитории. Кэш `~/.m2` сокращает прогон
с минут до секунд.

**Что сказать вслух:** «Минимальный CI — mvn verify на каждый PR + сборка и push
multi-arch образов по тегу v*. Дальше — dependabot на зависимости и базовые образы,
потому что тег temurin:21-jre плавающий: сегодня он 21.0.5, завтра 21.0.6, и образ
надо пересобирать осознанно».

### 🔴 3. Наблюдаемость: нельзя логировать, но можно измерять

**Проблема.** В проекте осознанно `slf4j-nop` — логировать нельзя (секреты). Но
без логов и метрик непонятно: сколько запросов, какие ошибки, не деградирует ли
сервис. «Ничего не пишем» — хорошо для безопасности, плохо для эксплуатации.

**Как сделать — метрики вместо логов.**
- Эндпоинт `GET /metrics` в формате Prometheus (текстовый, без библиотек — формат
  простой):
  ```
  genpass_requests_total{endpoint="/api/password",status="200"} 42
  genpass_request_duration_seconds_sum{endpoint="/api/password"} 0.83
  genpass_request_duration_seconds_count{endpoint="/api/password"} 42
  ```
- Счётчики: `AtomicLong`/`LongAdder` на (endpoint, status) — инкремент в
  `ApiHandlers`; гистограмма длительности — приблизительно через
  `DoubleAdder` суммы и счётчик (для LAN-инструмента точные бакеты не нужны).
- **Критично:** метрики считают запросы, статусы, байты, latency — **но не тела
  ответов**. Секрет в метрику не попадает по построению, а не по дисциплине.
- Дальше: Prometheus + Grafana на NAS (оба есть в Container Manager как пакеты)
  или просто `curl /metrics` для ручной проверки.

**Трейдоффы.** Ещё один endpoint = ещё одна поверхность атаки — можно отдавать
`/metrics` без секретов и с no-store; при желании — слушать на отдельном порту или
закрыть прокси-правилом. Для пет-проекта достаточно счётчиков в памяти (сброс при
рестарте допустим).

**Что сказать вслух:** «Логировать секреты нельзя в принципе — это не решается
дисциплиной, а решается архитектурно. Метрики дают наблюдаемость без утечек:
количество запросов, ошибки 4xx/5xx, latency. Это показывает понимание, что
безопасность и эксплуатация — не противоположности».

### 🟡 4. Virtual threads: Java 21 уже в проекте, а пул — из прошлой эпохи

**Проблема.** `Executors.newFixedThreadPool(4)` — модель «поток ОС на запрос из
ограниченного пула». Для CPU-bound генератора это работает, но: при росте числа
клиентов 4 потока станут узким местом (очередь в executor), а увеличение пула
упирается в ресурсы ОС.

**Как сделать.** Java 21 даёт virtual threads:
```java
server.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
```
Virtual thread стоит ~килобайты (против ~1 МБ стека потока ОС), создание —
наносекунды; можно дать **поток на каждый запрос** без риска исчерпания памяти.
Для сервера с блокирующим I/O (HttpServer именно такой) это фактически
бесплатный выигрыш в масштабируемости.

**Трейдоффы.** Для CPU-bound задач (наша генерация) выигрыша в скорости нет —
выигрыш в **конкурентности I/O**. Если бы в хендлерах были блокирующие вызовы
(БД, внешние API), виртуальные потоки были бы обязательны. Важно не злоупотреблять:
`pin`-сценарии (synchronized + блокирующий I/O) могут ухудшить ситуацию — в нашем
коде синхронизация только на загрузке словаря, так что риск нулевой.

**Что сказать вслух:** «Раз уж проект на Java 21 — я бы перевёл executor на virtual
threads: для блокирующего HttpServer это правильная модель, код меняется на одну
строку, а пул из 4 потоков перестаёт быть потолком масштабируемости. Для
CPU-bound-части это ничего не ухудшает».

### 🟡 5. Rate limiting: защита от злоупотребления эндпоинтами

**Проблема.** `POST /api/password` можно дёргать бесконечно: (а) расход ресурсов
(CPU на генерацию, сеть); (б) парсер JSON и лимит 64 КБ защищают от больших тел, но
не от частоты; (в) если сервис когда-нибудь станет публичным — это готовый вектор
DoS.

**Как сделать (минимально, без библиотек):**
- Fixed window на IP: `ConcurrentHashMap<String, Counter>` с окном 60 с, лимит
  например 60 запросов/мин на IP → 429 + заголовок `Retry-After`.
- Чистка старых окон по расписанию или лениво при обращении (иначе — утечка памяти
  на уникальных IP).

**Трейдоффы — и вот тут интересно для собеседования:** in-memory лимит ломает
**state-less архитектуру**: при двух репликах лимит считается раздельно (в два раза
больше запросов), при рестарте — сбрасывается. Честные варианты: (а) признать, что
приложение однопроцессное на NAS, и in-memory лимита достаточно; (б) вынести
лимитирование на reverse-proxy (`limit_req` в nginx — бесплатно и не трогает код);
(в) для горизонтального масштаба — Redis-счётчик, но это противоречит «ноль
зависимостей». Правильный middle-ответ: **сначала прокси, код не усложнять**.

**Что сказать вслух:** «Я бы начал с limit_req на nginx — код не меняется вовсе.
Если нужно в самом приложении — fixed window в памяти, честно понимая, что это
работает для одного процесса. Redis добавлял бы только при реальном
горизонтальном масштабировании, которого у state-less LAN-сервиса нет».

### 🟡 6. Graceful shutdown: довести до конца

**Проблема.** Сейчас остановка: shutdown-hook → `server.stop(1)` (ждёт до 1 с на
завершение активных exchange) → `executor.shutdown()`. Но: `shutdown()` не ждёт
завершения задач — JVM может умереть в середине ответа; таймаут 1 с может не
хватить при долгих запросах; при `docker stop` контейнер получает SIGTERM и через
10 с (дефолт) — SIGKILL.

**Как сделать.**
```java
server.stop(5);                 // до 5 с на завершение обработки exchange
executor.shutdown();
if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
    executor.shutdownNow();     // жёсткий откат для «зависших»
}
```
Плюс в docker-compose: `stop_grace_period: 20s`, чтобы контейнер успел завершиться
до SIGKILL. В оркестраторе (K8s) — `terminationGracePeriodSeconds` и preStop-hook
со сном для балансировщика.

**Трейдоффы.** Слишком долгий grace-период задерживает деплой/рестарт; слишком
короткий — режет живые запросы. 5–10 с для LAN-инструмента — разумный компромисс.

**Что сказать вслух:** «Полный цикл: перестать принимать новое → дать текущим
запросам до N секунд → принудительно отменить оставшиеся → дождаться пула →
сообщить оркестратору. И согласовать таймауты приложения с stop_grace_period
контейнера, иначе docker убьёт процесс раньше, чем он успеет попрощаться».

### 🟡 7. CVE и зависимости: плавающие теги и устаревшие версии

**Проблема.** (а) Версии зависимостей зафиксированы — хорошо; (б) но базовые

**Трейдоффы.** Dependency-check ложноположит на test-scope — фильтровать;
digest-пины требуют дисциплины обновления (автоматизация через Renovate/Dependabot).

**Что сказать вслух:** «Зависимостей в рантайме всего две (jackson, slf4j) — это

зависимостей — меньше работы, но не ноль».

### 🟢 8. Мелкие улучшения (говорить, только если спросят «а ещё?»)

- **Полевые ошибки валидации.** Сейчас 400 с одним сообщением; при нескольких
  ошибках клиент чинит по одной. Формат `{"errors": [{"field": "length", "message":
  "..."}]}` — дороже на грамм, удобнее на килограмм.
- **Сжатие статики.** index.html/app.js/style.css отдаются без gzip; для LAN
  некритично, но `Content-Encoding: gzip` на статике — три строки кода
  (с проверкой `Accept-Encoding`).
- **ETag/Last-Modified для статики.** `Cache-Control: no-cache` + ETag позволяет
  браузеру не качать файлы заново (условный GET → 304). Для NAS в LAN выигрыш
  небольшой, но это «правильный» HTTP.
- **Тест-профиль для статистики.** 100k-генерации в отдельном TestNG-группе
  (`groups = "slow"`), чтобы быстрый прогон в CI не тащил статистику — хотя 0.5 с
  уже приемлемо, это вопрос гигиены.
- **API-версионирование.** `/api/v1/password` — если эндпоинты изменятся,
  старые клиенты не сломаются. Для пет-проекта — на вырост.
- **Проверка доступности UI (a11y).** Прогнать axe-core: контраст уже выдержан
  (≥4.5:1), но автоматическая проверка aria-атрибутов вкладок и фокус-порядка
  поймает то, что глаз не видит.
- **prefers-color-scheme.** Если вернётся светлая тема — не второй файл, а
  CSS-переменные под media-query: вся тема уже в токенах `:root`, добавить
  `@media (prefers-color-scheme: light) { :root { ... } }` — полчаса работы.
  Сейчас тема одна, тёмная — осознанное решение пользователя.
